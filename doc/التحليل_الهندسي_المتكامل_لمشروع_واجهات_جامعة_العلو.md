# التحليل الهندسي المتكامل لمشروع واجهات جامعة العلوم والتكنولوجيا

## Frontend فقط باستخدام بيانات وهمية

**إصدار الوثيقة:** 1.0  
**نطاق المشروع:** واجهة أمامية فقط  
**نوع التطبيق:** React Web Frontend Prototype  
**اللغة الأساسية:** العربية مع دعم اتجاه RTL  
**مصدر البيانات:** ملفات JSON وبيانات محلية وهمية  
**لا يتضمن المشروع:** Backend، قاعدة بيانات، API، مصادقة حقيقية، دفع إلكتروني، أو اتصال بأنظمة الجامعة الفعلية

---

## 1. الملخص التنفيذي

يهدف المشروع إلى بناء واجهة ويب حديثة وتفاعلية لجامعة العلوم والتكنولوجيا، بحيث تقدم تجربة رقمية واضحة للزوار والطلاب والمتقدمين الجدد. يتكون النظام من بوابة عامة للتعريف بالجامعة والكليات والتخصصات والأخبار، إضافة إلى بوابة طالب تجريبية تعرض لوحة معلومات أكاديمية باستخدام بيانات وهمية.

يُنفذ المشروع بالكامل على مستوى الواجهة الأمامية. ولذلك فإن عمليات تسجيل الدخول، إرسال طلب القبول، عرض الدرجات، الجدول الدراسي، والحالة المالية ستكون **محاكاة بصرية وتفاعلية** داخل المتصفح، دون إرسال بيانات إلى خادم أو حفظها في قاعدة بيانات حقيقية.

الهدف الأساسي ليس بناء نظام جامعي خلفي، وإنما بناء نموذج Frontend احترافي قابل للعرض والتجربة، يوضح شكل المنتج النهائي، ويثبت جودة تجربة المستخدم، وتنظيم الصفحات، وسهولة التنقل، واستجابة التصميم على مختلف الشاشات.

> **حدود مهمة:** أي معلومة تظهر في لوحة الطالب أو نموذج القبول هي بيانات تجريبية لغرض العرض فقط، ولا تمثل سجلاً أكاديمياً أو مالياً حقيقياً.

## 2. أهداف المشروع

### 2.1 الأهداف الرئيسية

يهدف المشروع إلى إنشاء واجهة جامعية رقمية تتميز بالوضوح والسرعة وسهولة الاستخدام، وتحقق الأهداف التالية:

1. تقديم واجهة تعريفية احترافية تعكس هوية الجامعة.
2. مساعدة الطالب الجديد على استكشاف الكليات والتخصصات بطريقة تفاعلية.
3. عرض المستقبل الوظيفي لكل تخصص بصورة واضحة ومقنعة.
4. توفير نموذج قبول إلكتروني متعدد الخطوات لأغراض المحاكاة.
5. إنشاء لوحة طالب تجريبية تعرض البيانات الأكاديمية بصورة منظمة.
6. توفير تجربة متجاوبة تعمل على الهاتف واللوحي والحاسوب.
7. بناء مكونات قابلة لإعادة الاستخدام تسهّل التطوير والتعديل.
8. إظهار حالات الواجهة المختلفة، مثل التحميل والنجاح والخطأ والحالة الفارغة.

### 2.2 الأهداف غير المشمولة

لا يشمل المشروع تنفيذ أي من الوظائف التالية:

| الوظيفة | حالة التنفيذ |
|---|---|
| إنشاء قاعدة بيانات حقيقية | غير مشمولة |
| ربط API أو Backend | غير مشمول |
| تسجيل دخول حقيقي | غير مشمول؛ سيتم تنفيذ محاكاة فقط |
| التحقق من الهوية | غير مشمول |
| إرسال طلب قبول فعلي | غير مشمول؛ سيتم عرض رسالة نجاح وهمية |
| الدفع الإلكتروني | غير مشمول |
| تعديل سجلات الطلاب الحقيقية | غير مشمول |
| إرسال بريد أو رسائل SMS | غير مشمول |
| لوحة تحكم إدارية حقيقية | غير مشمولة، ويمكن تمثيلها بصرياً لاحقاً |

## 3. فئات المستخدمين

رغم أن المشروع Frontend فقط، يجب تصميم الواجهات وفقاً لاحتياجات الفئات المستهدفة.

| الفئة | هدف المستخدم من الواجهة |
|---|---|
| الزائر العام | التعرف على الجامعة وبرامجها وأخبارها ومرافقها. |
| الطالب المحتمل | مقارنة التخصصات ومعرفة مجالات العمل وشروط القبول. |
| المتقدم الجديد | تعبئة نموذج قبول تجريبي ومراجعة معلوماته. |
| الطالب الحالي | استعراض لوحة الطالب والجدول والدرجات والرسوم الوهمية. |
| المرشد أو الموظف | يمكن تمثيله بصرياً مستقبلاً، لكنه ليس ضمن النطاق الحالي. |

## 5. تفاصيل صفحات البوابة العامة

### 5.1 الصفحة الرئيسية

تُعد الصفحة الرئيسية نقطة الدخول الأساسية، ويجب أن توصل هوية الجامعة وقيمتها خلال ثوانٍ قليلة.

#### الأقسام المقترحة

1. شريط علوي يحتوي على رقم الهاتف والبريد وروابط التواصل.
2. Header يتضمن شعار الجامعة والقائمة الرئيسية وزر القبول.
3. Hero Section بصورة أو تصميم بصري يعكس الحرم الجامعي.
4. عنوان رئيسي واضح مثل: «ابنِ مستقبلك الأكاديمي والمهني معنا».
5. أزرار إجراءات رئيسية مثل «استكشف التخصصات» و«ابدأ طلب القبول».
6. شريط أخبار مختصر للإعلانات المهمة.
7. إحصائيات مرئية، مثل عدد الكليات والبرامج والخريجين، على أن تكون جميعها وهمية.
8. قسم الكليات أو أبرز التخصصات.
9. قسم يشرح لماذا يختار الطالب الجامعة.
10. قسم خطوات القبول في ثلاث أو أربع مراحل.
11. آخر الأخبار والفعاليات.
12. Footer شامل للروابط ومعلومات التواصل.

#### حالات الصفحة

يجب تصميم الصفحة لحالات البيانات الطبيعية، وقلة الأخبار، وعدم وجود صورة، وحالة التحميل الوهمية. وفي حالة عدم توفر عنصر معين، لا ينبغي أن ينهار التصميم أو تظهر مساحات غير منظمة.

### 5.2 صفحة الكليات

تعرض الصفحة جميع الكليات في شبكة بطاقات متجاوبة. تحتوي بطاقة الكلية على الاسم، الوصف المختصر، الصورة أو الأيقونة، عدد التخصصات، وزر الانتقال إلى التفاصيل.

#### وظائف الواجهة

- البحث باسم الكلية.
- التصفية حسب المجال الأكاديمي.
- عرض حالة عدم وجود نتائج.
- فتح تفاصيل الكلية.
- دعم العرض الشبكي على الشاشات الكبيرة والعرض العمودي على الهاتف.

### 5.3 صفحة تفاصيل الكلية

تتضمن الصفحة غلافاً بصرياً للكلية، نبذة عنها، قائمة التخصصات، معلومات مختصرة عن مجالات الدراسة، وأزرار الانتقال إلى تفاصيل كل تخصص أو صفحة القبول.

### 5.4 صفحة تفاصيل التخصص

هذه الصفحة من أهم أجزاء المشروع؛ لأنها لا تكتفي بعرض اسم التخصص، بل تساعد الطالب على فهم قيمته الأكاديمية والمهنية.

#### الأقسام المقترحة

| القسم | المحتوى |
|---|---|
| التعريف | اسم التخصص ورمز تجريبي ووصف مختصر. |
| لماذا هذا التخصص؟ | الفائدة والأهمية بأسلوب مفهوم للطالب. |
| ماذا ستتعلم؟ | المهارات والموضوعات الرئيسية. |
| الخطة الدراسية | مواد نموذجية موزعة على سنوات أو مستويات. |
| المستقبل الوظيفي | الوظائف والمسارات المهنية المحتملة. |
| المهارات المطلوبة | مهارات تقنية وشخصية مقترحة. |
| معلومات الدراسة | مدة الدراسة ونوع الدرجة بشكل تجريبي. |
| الدعوة للإجراء | زر «ابدأ طلب القبول» وزر «قارن تخصصاً آخر». |

### 5.5 صفحة القبول والتسجيل

تعرض الصفحة خطوات القبول بصورة مبسطة، والوثائق المطلوبة بشكل تجريبي، والأسئلة الشائعة، ثم زر بدء نموذج التقديم.

يجب أن تكون الصفحة موجهة للطالب الجديد، لذلك ينبغي استخدام لغة بسيطة، وتجنب المصطلحات الإدارية المعقدة، وتقسيم المعلومات إلى أجزاء قصيرة قابلة للمسح البصري.

### 5.6 نموذج القبول متعدد الخطوات

يكون النموذج تجريبياً، ولا يرسل البيانات إلى أي جهة. يمكن حفظ المدخلات مؤقتاً في حالة React أو LocalStorage لأغراض تجربة الانتقال بين الخطوات فقط.

#### الخطوات

| الخطوة | الحقول أو المحتوى |
|---|---|
| 1. البيانات الشخصية | الاسم، تاريخ الميلاد، الجنس، رقم الهاتف، البريد. |
| 2. البيانات التعليمية | المدرسة، سنة التخرج، النسبة، المؤهل. |
| 3. اختيار الدراسة | الكلية، التخصص، نظام الدراسة، الرغبة الأولى والثانية. |
| 4. المراجعة | عرض جميع البيانات قبل التأكيد. |
| 5. النتيجة | رسالة نجاح وهمية مع رقم طلب تجريبي. |

#### قواعد التحقق في الواجهة

- منع الانتقال إلى الخطوة التالية عند وجود حقل مطلوب فارغ.
- التحقق من شكل البريد الإلكتروني.
- التحقق من طول رقم الهاتف بصورة تجريبية.
- إظهار رسالة خطأ بجانب الحقل المتسبب في المشكلة.
- حفظ البيانات عند العودة إلى خطوة سابقة.
- إظهار مؤشر يوضح الخطوة الحالية والمتبقية.
- السماح بالعودة إلى الخطوات السابقة دون فقد البيانات.

### 5.7 صفحة الأخبار

تعرض الأخبار على شكل بطاقات تتضمن الصورة والعنوان والتاريخ والتصنيف والملخص. يجب توفير بحث وتصفية شكلية حسب التصنيف، مثل أخبار الجامعة والقبول والفعاليات والأنشطة الطلابية.

### 5.8 صفحة تفاصيل الخبر

تحتوي على العنوان، التاريخ، صورة الغلاف، محتوى منسق، أخبار ذات صلة، وزر العودة إلى الأخبار. يمكن استخدام بيانات نصية وهمية طويلة لاختبار القراءة والتخطيط البصري.

### 5.9 صفحة 404

ينبغي تصميم صفحة غير موجودة بشكل واضح، مع رسالة ودية وزر للعودة إلى الصفحة الرئيسية وزر لاستكشاف الكليات.

## 6. تفاصيل بوابة الطالب التجريبية

### 6.1 صفحة تسجيل الدخول

تنفذ الصفحة محاكاة بصرية لتسجيل الدخول باستخدام الرقم الجامعي وكلمة مرور تجريبية. لا توجد مصادقة فعلية ولا اتصال بخادم.

#### السيناريوهات المطلوبة

| السيناريو | السلوك المتوقع |
|---|---|
| بيانات صحيحة تجريبياً | الانتقال إلى لوحة الطالب وإظهار رسالة ترحيب. |
| بيانات ناقصة | عرض رسائل تحقق بجانب الحقول. |
| بيانات غير صحيحة | عرض رسالة خطأ وهمية. |
| إظهار كلمة المرور | تبديل حالة الإخفاء والإظهار. |
| تذكر الدخول | حفظ حالة وهمية محلياً إن لزم. |
| العودة للبوابة العامة | توفير رابط واضح للصفحة الرئيسية. |

### 6.2 تخطيط لوحة الطالب

تتكون لوحة الطالب من Sidebar على الحاسوب وقائمة قابلة للفتح على الهاتف، إضافة إلى Header يعرض اسم الطالب وإشعارات وهمية وقائمة الحساب.

#### عناصر اللوحة

- اسم الطالب وصورته الرمزية.
- الرقم الجامعي التجريبي.
- الفصل الدراسي الحالي.
- بطاقة المعدل التراكمي.
- بطاقة الساعات المنجزة.
- بطاقة الحضور أو الحالة الأكاديمية.
- بطاقة الرسوم الوهمية.
- جدول مختصر لمحاضرات اليوم.
- آخر الإعلانات.
- اختصارات للسجل والجدول والملف الشخصي.

### 6.3 صفحة الجدول الدراسي

تعرض الجدول على شكل شبكة أسبوعية للحاسوب، وعلى شكل بطاقات يومية للهاتف. ينبغي توفير تحديد اليوم أو الأسبوع، وتمييز المحاضرة الحالية بلون مختلف، وعرض اسم المقرر والقاعة واسم المدرس والوقت.

### 6.4 صفحة السجل الأكاديمي

تعرض الفصول الدراسية في تبويبات أو قائمة قابلة للفتح، مع جدول يوضح اسم المقرر والرمز والساعات والدرجة والتقدير. أسفل الجدول يظهر المعدل الفصلي والتراكمي كبيانات وهمية.

### 6.5 صفحة الحالة المالية

تستخدم بيانات تجريبية فقط لعرض رسوم دراسية ومبالغ مسددة ومتأخرة. يجب توضيح داخل الواجهة أن المعلومات غير حقيقية. لا يتضمن المشروع أي زر دفع أو تحويل مالي.

### 6.6 الملف الشخصي والإعدادات

يعرض الملف الشخصي البيانات الوهمية للطالب، بينما تسمح الإعدادات بتغيير المظهر بين الوضع الفاتح والداكن، وضبط الإشعارات الوهمية، واختيار اللغة إن تم دعم العربية والإنجليزية.

## 7. معمارية الواجهة الأمامية

### 7.1 التقنية المقترحة

| العنصر | الاختيار المقترح |
|---|---|
| الإطار | React مع Vite فقط، دون Next.js أو أي إطار بديل. |
| اللغة | TypeScript لتقليل أخطاء أنواع البيانات. |
| التصميم | Tailwind CSS مع ملف توكنات للهوية البصرية. |
| التنقل | React Router لإدارة مسارات تطبيق React. |
| إدارة الحالة | Zustand أو Context API للحالة المحلية البسيطة. |
| النماذج | React Hook Form مع تحقق محلي. |
| الحركات | Framer Motion للحركات المحدودة والهادفة. |
| الأيقونات | مكتبة أيقونات موحدة مثل Lucide React. |
| الاختبار | Vitest وReact Testing Library لاختبار الواجهات. |

تم اعتماد React مع Vite بشكل نهائي لهذا المشروع. ويُستخدم React لبناء الواجهات والمكونات، بينما يوفر Vite بيئة تطوير وتشغيل سريعة ومناسبة لمشروع Frontend يعتمد على بيانات وهمية محلية.

## 9. الهوية البصرية ونظام التصميم

### 9.1 الاتجاه البصري

يُقترح استخدام أسلوب جامعي حديث يجمع بين الرسمية والوضوح. تكون الألوان الرئيسية هادئة ومناسبة للهوية الأكاديمية، مع استخدام لون إبراز للأزرار والروابط والتنبيهات.

| العنصر | المقترح |
|---|---|
| اللون الأساسي | أزرق داكن يعبر عن الثقة والاستقرار. |
| اللون الثانوي | تركواز أو أخضر مزرق للعناصر التفاعلية. |
| لون الإبراز | ذهبي أو برتقالي هادئ للأزرار المهمة. |
| الخلفيات | أبيض ورمادي فاتح مع أقسام ملونة محدودة. |
| النص الأساسي | رمادي داكن عالي الوضوح. |
| الخط | خط عربي واضح ومتناسق مع خط لاتيني عند الحاجة. |
| الزوايا | متوسطة الاستدارة للبطاقات والأزرار. |
| الظلال | خفيفة وغير مبالغ فيها. |

### 9.2 مبادئ التصميم

ينبغي الحفاظ على اتساق المسافات وأحجام العناوين وأشكال الأزرار في جميع الصفحات. يجب ألا تُستخدم الحركات لمجرد الزينة، بل لتوضيح الانتقال أو تأكيد الإجراء. كما يجب ألا تعتمد المعلومات على اللون وحده، خصوصاً في حالات النجاح والخطأ والتنبيهات.

### 9.3 دعم RTL

يجب بناء التخطيط من البداية ليدعم اتجاه RTL، وليس مجرد عكسه في نهاية المشروع. يشمل ذلك اتجاه القوائم، موضع الأيقونات، محاذاة النصوص، الجداول، التدرج البصري، الحواف، الأسهم، والتنقل بين خطوات النموذج.

## 12. الوصولية وقابلية الاستخدام

يجب أن تكون الواجهة قابلة للاستخدام من أكبر عدد ممكن من المستخدمين. ويتضمن ذلك استخدام عناصر HTML الدلالية، وضبط تسلسل العناوين، وإضافة تسميات للحقول، وإظهار التركيز عند التنقل بلوحة المفاتيح، وتوفير نص بديل للصور، والحفاظ على تباين مناسب.

في النوافذ المنبثقة، يجب نقل التركيز إلى النافذة عند فتحها، ومنع التفاعل العرضي مع الخلفية، وإتاحة الإغلاق بزر Escape. وفي النماذج، ينبغي ربط رسالة الخطأ بالحقل الصحيح وإبلاغ المستخدم بما يجب تصحيحه.

## 13. الاختبارات المطلوبة

### 13.1 اختبار المكونات

يتم اختبار الأزرار، الحقول، البطاقات، النوافذ المنبثقة، التنبيهات، الجداول، مؤشرات التحميل، وحالات الخطأ بصورة مستقلة.

### 13.2 اختبار الصفحات

يجب التأكد من أن كل مسار يفتح الصفحة الصحيحة، وأن الروابط الداخلية تعمل، وأن زر العودة يحافظ على توقع المستخدم، وأن صفحة 404 تظهر للمسارات غير المعروفة.

### 13.3 اختبار نموذج القبول

يشمل الاختبار الانتقال بين الخطوات، التحقق من الحقول، حفظ القيم، العودة إلى الخطوات السابقة، منع الإرسال عند وجود أخطاء، عرض ملخص المراجعة، وإظهار النتيجة النهائية الوهمية.

### 13.4 اختبار الاستجابة

يجب اختبار الواجهة على الهاتف واللوحي والحاسوب، مع التركيز على Header، القوائم، الجداول، النوافذ، النماذج، البطاقات، والصور.

### 13.5 معايير القبول العامة

| المعيار | النتيجة المطلوبة |
|---|---|
| التنقل | جميع المسارات والروابط الداخلية تعمل. |
| RTL | لا توجد عناصر مقلوبة أو محاذاة غير صحيحة. |
| الهاتف | لا يحدث قص أفقي غير مقصود باستثناء الجداول المصممة للتمرير. |
| النماذج | تظهر الأخطاء بجانب الحقول المناسبة. |
| البيانات | لا توجد بيانات مكررة داخل المكونات دون سبب. |
| الحالات | لكل شاشة حالة تحميل وفراغ وخطأ عند الحاجة. |
| الوصولية | يمكن استخدام العناصر الأساسية بلوحة المفاتيح. |
| الأداء | لا توجد صور ضخمة أو حركات تسبب بطئاً ملحوظاً. |
| التناسق | الأزرار والبطاقات والعناوين موحدة بصرياً. |

## 17. القرار التقني النهائي المقترح

لأن المشروع Frontend فقط ويستخدم بيانات وهمية، فإن الخيار المقترح هو:

> **React + TypeScript + Vite + Tailwind CSS + React Router + Zustand أو Context API + React Hook Form + Framer Motion.**

تم اعتماد React كتقنية الواجهة الأمامية الأساسية والوحيدة في المشروع، مع استخدام Vite لإدارة بيئة التطوير والبناء. ويستخدم React Router لتنظيم المسارات، بينما يوفر Tailwind CSS سرعة في بناء الواجهات المتجاوبة. يمكن استخدام Zustand إذا زادت الحالة المشتركة بين الصفحات، أما Context API فيكفي للحالات البسيطة مثل المظهر أو بيانات الطالب التجريبية.

لا يتضمن المشروع استخدام Next.js أو أي إطار واجهات بديل؛ لأن النطاق المعتمد هو تطبيق React Frontend مستقل يعمل ببيانات وهمية محلية.

## 18. الخلاصة النهائية

هذا التحليل يحدد نظام Frontend متكاملاً لجامعة العلوم والتكنولوجيا، ويغطي البوابة العامة، الكليات، التخصصات، التوجيه الأكاديمي، الأخبار، نموذج القبول، وتطبيق الطالب التجريبي. وقد تم استبعاد Backend وقاعدة البيانات وواجهات API والمصادقة الحقيقية والدفع الإلكتروني بشكل صريح.

يُنفذ النظام باستخدام بيانات وهمية محلية، مع التركيز على جودة تجربة المستخدم، وضوح التنقل، دعم العربية وRTL، الاستجابة لمختلف الشاشات، إعادة استخدام المكونات، محاكاة الحالات المختلفة، وإمكانية اختبار الواجهة بصورة عملية.

وبذلك يصبح المشروع مناسباً كنموذج Frontend احترافي قابل للعرض، ويمكن لاحقاً ربطه بأي Backend دون إعادة بناء الواجهة بالكامل، لأن البيانات والمكونات والمسارات منظمة في طبقات منفصلة.

> **الحكم النهائي:** التحليل بعد اعتماد هذه الحدود يُعد وثيقة نطاق وتصميم Frontend متكاملة وقابلة للبدء في التنفيذ، بشرط الالتزام بأن جميع العمليات والبيانات داخل المشروع تجريبية ومحلية فقط.
